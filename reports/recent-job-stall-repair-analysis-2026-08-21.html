02 / SCOPE

范围、样本与判定口径

避免把同一个失败码的重试次数误当成不同问题，也避免把暂未再现误判为永久解决。

样本定义

纳入数据库中创建于 2026-08-12 00:00 UTC 之后、截至 2026-08-20 有执行记录的 13 个 Wiki 生产 Job，目标涵盖 P030、A001、P026、A015、A040、A037、A039、A014、A013。

所有这些 Job 都处于 publication_mode=preview。因此 candidate / diagnostic_preview 只代表预览流水线终态，不代表 reviewed publish 完成。

三层复发判定

  1. 失败码复发：同一 code 出现在多个 Job。
  2. 根因复发：同一 cause_code 出现在多个 Job。
  3. 机制复发：即使 cause_code 不同，仍落在同一系统机制，如“修复输入未变化”或“抽取零产出”。

报告中的“已修复”必须至少有后续成功尝试或验证回执；“未再现”还必须说明观察窗口与独立样本数量。

08 / AUTONOMY

设计缺陷 1：诊断不能沉淀

50 个根因码中 44 个只出现一次，说明 causal diagnosis 更像自由文本命名，而不是稳定本体。同一 editorial 机制被拆成 capacity blind、one-to-many、delete unrepresentable、list relocation、identity suffix 等大量标签，Supervisor 很难直接命中已有修复策略。

设计缺陷 2：修复成功判定过窄

A013 两个 receipt 标为 effective 后，同一路径仍继续失败；receipt payload 中甚至记录 closer_to_modelling_goal=false。验证只证明局部 patch / test 通过，没有证明 Job 的目标质量向量改善。

设计缺陷 3：只修补当前 validator

08-20 在不到 90 分钟内连续 10 个 editorial 提交，依次增加 capacity、cross-paragraph、relocation、split、feedback、merge、identity、duplicate 等能力。这是 schema chase：每次修掉一个表现，下一个不可表达操作继续暴露。

设计缺陷 4：终态吞掉质量债务

diagnostic_preview 允许 pipeline_continue，且 preview 模式跳过发布尾链。Supervisor 看到 workflow succeeded 后停止，而用户目标是 golden-case 级完整内容。这不是模型不够努力，而是 Goal Contract 与终态机定义错位。

总体判断：自治模块“会发现问题”，但其闭环仍是局部的：发现的是 validator symptom，修复的是局部代码，验证的是测试或一次尝试，缺少以最终质量向量为准的跨阶段验收。因此问题会以新 failure_code / 新 cause_code 变体继续出现。
09 / ACTIONS

建议的修复优先级

目标是把“能继续跑”升级为“能证明完成”，并让已修问题真正成为系统经验。

P0 · 终态

把 preview 产物与 Job 完成状态彻底解耦

preview 只应是 artifact / milestone；若 Goal Contract 要求完整成功，0 采纳、0 填充、candidate_eligible=false 时 Job 必须保持 active、repairable 或 needs_evidence，不能进入 completed 语义。

KPI: false-complete = 0
P0 · 门禁

禁止空结果 GO

table population gate 至少要求：公开可提取字段非零、关键表填充率阈值、已抓取 payload 比例、accepted_evidence 非零；若确属内部数据需求，必须产生明确的数据请求，而不是空表成功。

KPI: 0/35 ⇒ BLOCK
P0 · 修复

effectiveness 必须绑定目标质量增量

repair receipt 同时验证 patch hash、因果输入 hash、失败 fingerprint 消失、质量向量改善、后续 N 个阶段不回归。只通过单测或单次 gate 不得标 effective。

KPI: false-effective = 0
P1 · 本体

建立稳定 failure mechanism family

新增标准层：runtime/protocol、research-contract、fetch-route、extractor-yield、editorial-schema、causal-feedback、identity-lineage、terminal-semantics。cause_code 作为实例，family 作为策略索引。

KPI: singleton < 40%
P1 · 规划

从 patch retry 升级为 bounded replanning

同一 family 连续 2 次且 causal input hash 不变时，禁止再次随机生成；必须重建 research route、content blueprint 或 operation plan。连续 3 次则升级为 system repair / human approval。

KPI: unchanged retry = 0
P1 · 证据

修复 fetch → route → extract → select 的闭环

对 PDF / HTML 文献记录每一步：查询词、数据源、候选、抓取状态、payload hash、route、抽取观察、采纳/拒绝原因。Cisco LCA PDF 这类高相关文献不能以 payload_not_fetched 静默落入 evidence_limited。

KPI: fetched payload ≥ 95%
P2 · 评估

建立独立 post-fix replay corpus

每个 promoted repair 必须在原 Job、相邻节点、新建独立 Job 三层回放；至少观察一个后续独立 Job 后，才允许标注“未再现”。

KPI: 3-level replay
P2 · 看板

把修复谱系与质量债务作为一等信息

在 Job 页展示 failure family、causal input diff、修复提交 / PR、验证回执、查询漏斗、被拒证据理由、当前未满足的 Goal Contract；不要只展示 task succeeded。

KPI: explainability 100%

报告结论：系统目前具备发现、生成修复、测试和继续执行的基本能力，但尚未形成以最终生产质量为中心的自治闭环。最优先的工作不是增加更多重试，而是修正完成语义、空结果门禁和 repair effectiveness 证明。
