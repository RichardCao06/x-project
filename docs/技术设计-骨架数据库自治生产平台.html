01 / 16

执行摘要

项目应从“人通过对话临时编排 Agent 和脚本”升级为“目标驱动、事件驱动、Artifact 驱动”的自治知识生产系统。

核心结论
本项目不需要一个更强的“超级 Agent”，而需要一个长期运行的控制平面。Agent 可以犯错，但必须无法无证写入、无法静默漏做、无法给自己签字；错误应由独立机制发现、回滚并生成修复任务。

从哪里出发

仓库已拥有名称图 Gate、跨行业 lint、Wiki 批次状态机、BOM 探针和 LCA 绑定等执行原语，但入口、状态、协议和发布语义分散。

建设什么

建设统一 Kernel、Capability Registry、声明式 Workflow、不可变 Artifact Store、分层 Gate、Repair Controller 和异常队列。

最终状态

系统持续扫描全局缺口，自动生成任务、调用脚本与 Agent、验证和发布低风险变更；人只维护政策、裁决异常和执行专家签署。

预期收益

维度当前形态目标形态
驱动方式对话中由人逐步推进Desired State 与仓库现状自动对账
Agent 角色兼任计划、执行、检查和汇报只做候选生成或独立语义裁决
运行状态散落在聊天、文件名和局部 journal统一 State DB + Event Log
产物脚本直接写共享目录不可变 Artifact，经 Gate 后原子发布
失败处理人阅读日志后重新发起对话执行自愈、目标偏离诊断、最小重放或隔离
质量声明多个局部 PASS 容易被外推为整体完成每个 Gate 明示证明范围，发布资格独立计算
系统迭代用户反馈后人工修改 Gate 或脚本偏离聚类、隔离变更、Golden/Mutation/Canary 验证后晋级
02 / 16

背景与问题定义

方法论和局部 Workflow 已较成熟，但执行仍依赖人在对话中维持全局上下文，导致规则落实、状态连续性和错误恢复缺乏系统保证。

现有优势

  • 名称图已建立 Product / Activity、PRODUCES / CONSUMES、身份刻面和 A–E 不变量。
  • gate.py 已实现物化、对账、11/11 校验和原子发布。
  • wiki_batch.py 已实现计划、准备、核验、冻结、Gate、Apply、Publish 和 resume。
  • 跨行业 GPID、BOM 探针、产品系统树和 LCA 数据集绑定均已有可复用脚本。
  • 节点 Wiki 复盘已经积累大量真实失败样本，可作为缺陷语料库。

结构性问题

控制问题

  • 全局下一步由对话决定。
  • 多个入口实现相近流程。
  • 局部 journal 不能形成全仓状态。
  • 失败后依赖人工解释日志。

质量问题

  • 来源通过被误当成断言通过。
  • Gate 覆盖范围未被显式表达。
  • Agent 运行模型、工具和预算可能漂移。
  • 抽样完成容易被外推为全量完成。
设计边界：本方案不能证明开放领域知识“绝对无错”，也不取消专家对边界、刻面、数据代表性和定量值的责任。它要保证的是：错误影响有界、不可静默发布、可以追溯、可以回滚，并能把已知错误转化为永久防线。
03 / 16

目标、非目标与设计原则

所有模块、Skill、Workflow、脚本和 Agent 都必须服从同一组项目级不变量。

建设目标

  • 自动发现整个骨架数据库的行业、节点、分类、接口、Wiki 和绑定缺口。
  • 自动生成可重放 Job，并按依赖、风险、价值和预算调度。
  • 将 Agent 限制为可验证的候选生成器或裁决器。
  • 所有写入经过分层 Gate、事务 Apply、版本发布和发布后验证。
  • 低风险任务逐步实现无人值守，高风险任务自动转入最小异常包。

非目标

  • 不构建一个拥有无限权限、可直接编辑全仓的超级 Agent。
  • 不将聊天历史作为生产状态或权威知识。
  • 不以一个“总分”替代图、证据、内容、绑定和发布的分层质量声明。
  • 不在第一阶段引入重型分布式编排平台或一次性重写所有脚本。

六条硬原则

Job 驱动

每次工作必须来自持久化 Job，输入、预算、权限、结果和状态转移均可重放。

无直接写入

Agent 只提交 proposal 或 verdict；权威文件只能由受控 Apply capability 修改。

不可变产物

中间结果内容寻址、只增不改；新的计算产生新 Artifact，而不是覆盖历史。

证明后发布

发布必须携带输入哈希、运行证明、Gate 报告、政策版本和回滚目标。

集合守恒

应处理、已提名、已检索、已核验、已写入和已发布的集合逐层对账，禁止静默漏项。

缺陷固化

每个逃逸错误必须形成 fixture、mutation 或政策测试，并追溯扫描既有发布物。

跨模块问题如何处理

例如 Wiki 发现节点身份可能有误时，只发布 graph.identity_issue_detected，由 Planner 生成图修复任务。Wiki 不得直接修改名称图。图修复发布后，影响分析器根据 spine hash 自动使相关 Wiki、跨链和绑定进入 stale 状态并重建。

Skills、Memory、脚本与 Workflow 的统一管理

四类组件必须拥有清晰的职责和唯一权威来源，避免同一规则散落在 AGENTS、Skill、方法文档、Prompt 和脚本中。

组件负责什么不负责什么权威载体
Skill意图路由、参数收集、状态解释、异常交互生产状态、业务真相、直接写文件Skill package + workflow reference
Memory政策、结构化决策、运行历史、缺陷经验未验证聊天结论、隐式下一步Policy / ADR / State DB / Defect Corpus
Script单一、确定性、幂等 Capability全局编排、自由语义判断、越权发布Capability manifest + executable
Agent候选生成或独立语义裁决自证、自签、直接 ApplyAgent definition + prompt + schema
Workflow声明步骤、依赖、重试、预算、分支和 Gate复制业务规则、内嵌大段实现Versioned workflow specification
Gate证明一个声明范围内的属性宣称超出覆盖范围的整体正确Gate capability + policy + tests

Skill：薄入口

当前 generate-node-wiki Skill 只负责校验节点参数并提交持久化 Job，绑定 workflow://wiki-node-production@6。它不解释方法论后临场选择脚本，不轮询长进程，不决定重试，也不保存状态机或自行 Apply。面向人的触发说明保留在标准 SKILL.md，机器路由独立存放于 skill.manifest.json；route manifest、请求 schema 和 policy 均作为冻结输入进入 Job lineage，实际步骤由 Orchestrator 物化。

  • 一节点一 Job：wiki-production-request-v2 强制一次只接受一个 P### 或 A###，不同节点不共享 Verify、预算、重试或发布资格。
  • 安全默认值：未明确要求正式审核发布时，publication_mode 默认为 preview。
  • 权限声明：route manifest 明确 Skill 可以创建 Job，但不能执行 capability、Apply 或 Publish。
  • 双哈希输入：请求 Artifact 与 route Artifact 同时进入 Job input hashes，Skill 路由变化会产生新的幂等身份。

Memory：四层分离

规范性 Memory

Policy 与机器可读规则，定义 Gate、预算、风险、状态和发布资格。

决策 Memory

版本化 ADR，保存原因、证据、适用范围、替代关系和生效版本。

运行 Memory

Job、Run、Event、Artifact、usage、lease、错误和恢复点。

临时 Context

单次 Agent 调用的冻结 dossier、精简索引、evidence 和 task policy。

正文与定量表分流

Version 6 在 Verify 后生成节点特定 Content Blueprint。正文叙事和定量表采集是两条独立证据流：正文可以使用已确认外部事实、内部图谱事实与显式建模判断；表格数值必须具有冻结参考配置、来源身份、单位和适用范围，并通过独立 Table Population Gate。两条流只在 draft apply 后按哈希汇合，避免“正文写得深”被误认为“数值已经可靠”。

证据按 A–E 分级：A 为同工厂同产品同边界的一手数据，B 为同型号或同企业过程资料，C 为同工艺相似产品代理，D 为多来源工程推导，E 为已证明的公共证据缺口。C/D 可以进入候选模型和敏感性分析，但必须显式显示代理角色、调整方法、失效条件和不确定性；E 必须生成企业数据请求，不能被空表或普通成功状态掩盖。

过程族文档路由

检索能力按过程族复用，而不是为每个节点手工堆查询。以 A039 所属的 server_final_assembly 为首个垂直样板，至少覆盖制造商 QuickSpecs/配置指南、维护与拆装手册、产品 PCF/EPD 技术附件、工厂环评与排污许可、过程 LCA/制造研究、Open Compute 与拆解报告。产品级 PCF 可作为质量和材料约束，但在无法分解时不得冒充整机总装单元过程。

L0 · 执行自愈

处理 Worker、Lease、Provider、缓存、I/O 和暂时性基础设施故障，不改变业务语义；每次恢复生成新的 Attempt 和证明。

L1 · Job 目标回归

自动补查询、查询级翻译、局部正文修复、表格缺口证明，并从最小失效节点重放；质量无改善时停止。

L2 · 系统自我迭代

将跨 Job 重复偏离升级为 Gate、Policy、Prompt、配置或代码变更候选，在隔离环境验证后逐步晋级。

L2 编码 Agent 的受治理执行链

Execution failure → deterministic fast path | read-only Failure Triage Agent
Successful low-utility research → Research Outcome Evaluator → read-only Research Triage Agent
        → evidence-backed causal route + questions + expected metric delta
        → System Change Candidate

编码 Agent 只写一次性快照，不能编辑 Goal Contract、修复权限、发布能力、密钥或生成的完整性清单；它也不能签发 Validation Certificate。控制平面独立计算补丁哈希和证书。中高风险候选即使测试通过也停在待批准状态；低风险候选才可自动晋级。验证或合入后回归失败时恢复原文件并记录拒绝/回滚凭证。

规则库不是修复入口白名单：已知模式用于低延迟确定性处理，未知失败自动进入 migration v9 持久化的只读 Agent Triage。首次未知失败的调查意图会持久化，即使快速重试暂时隐藏失败形态，下一次自治监督仍会消费；Triage 完成前不得生成猜测性的通用变更候选，并发监督也不得重启正在调查的 Run。Triage 基于冻结 dossier、DAG、上下游前置条件、Artifact、Goal Contract 与源码，自主输出问题类别、因果链、证据、修复层级、风险、恢复 Task、实现目标和 focused tests。指纹只用于去重与经验复用；写权限仍只在受治理的 L2 编码沙箱内授予。

Stage Supervisor：压平 Agent 编排开销

复盘显示，长任务的主要耗时不是测试或单个脚本，而是数百次“模型判断 → 小工具 → 等待 → 再判断”的串行往返，以及 10–15 秒间隔的长进程轮询。当前由 StageSupervisor 接管一个冻结阶段：命令顺序、重试、预期产物和输入哈希写入 plan；监督器使用阻塞式子进程等待，在内部完成循环，最终只返回一次 terminal summary。

硬预算

默认最多 100 个模型调用单位、100 个子进程和 7200 秒；第 101 次启动前强制 checkpoint。

零短轮询

执行层只使用有 timeout 的阻塞式 subprocess；不向 Agent 暴露 poll handle，不以日志片段驱动下一步。

可交接终态

成功、失败或预算停止都写入 SQLite、Event、CAS 和阶段专属 checkpoint，记录下一命令与冻结 plan hash。

stage-plan-v1
  stage_id / run_id / workspace
  frozen_inputs: path → sha256
  limits:
    max_model_calls: 100
    max_processes: 100
    max_elapsed_seconds: 7200
    max_compactions: 0
  commands[]:
    argv / timeout / max_attempts
    model_call_units / expected_outputs
宿主边界
项目进程不能自行感知 Codex 宿主发生 context compaction，也不能自行创建新的桌面任务。宿主必须把压缩次数通过 --compactions-observed 注入；一旦大于预算，监督器在启动任何子进程前生成 checkpoint。真正的新任务由桌面端或上层调度器创建，并消费该 checkpoint。

项目完成度定义

“整个骨架数据库完成”应由机器可计算的项目政策定义，包括：所有计划行业达到声明生命周期；图 Gate 全过；分类缺口已清或已解释；跨行业接口无未响应项；GPID 无断链；Wiki 达到规定覆盖；长尾和数据缺口显式；专家签署任务完成。项目进入维护态后，完成度仍会因新分类、新技术和新行业期望变化而重新计算。

关键架构决策

以下决策应进一步拆成版本化 ADR，并成为重构期间的边界护栏。

ADR-001
采用模块化单仓 + 本地控制平面，不立即拆成微服务。
ADR-002
第一阶段使用 SQLite 和本地内容寻址存储，保留迁移 PostgreSQL/对象存储的接口。
ADR-003
Agent 永不直接写权威库，只产生 proposal/verdict。
ADR-004
所有跨模块交互使用 Artifact 和 Event，不通过共享文件的隐式编辑。
ADR-005
Workflow 声明式、Capability 注册化、Agent 定义版本化。
ADR-006
Source verified、Claim verified、Wiki reviewed、Dataset ready 是四个独立状态。
ADR-007
Gate 必须声明证明范围；总发布资格由多个 Gate 组合计算。
ADR-008
复盘缺陷永久进入测试和追溯扫描，不允许只修当前样本。
ADR-009
人在主流程中逐步退出，但政策变更、身份边界和定量专家签署长期保留人工责任。
ADR-010
长阶段必须由非轮询 Stage Supervisor 执行；主 Agent 只规划、读取终态与组织最终验收。
ADR-011
单阶段硬上限为 100 个模型调用单位或首次宿主 compaction；超限生成 CAS checkpoint，不允许提示词软约束继续运行。
ADR-012
模型路由属于 Workflow：Terra 生产候选，Sol 执行证据核验和最终只读审查，禁止主会话隐式承担 Worker。
ADR-013
长正文最终审查采用确定性分节、受控并发和代码聚合；传输重试不得触发正文重写。
ADR-014
Goal Contract 是 Gate 的上位合同；Gate 只提供目标观测与执行许可，不能自行定义业务目标。
ADR-015
自我修复分为 L0 执行自愈、L1 Job 目标回归和 L2 系统迭代；运行中的 Job 不得直接修改线上代码、Goal Contract 或发布权限。
ADR-016
L2 行为变化必须生成独立验证证书，经过触发样本、Golden、Mutation、Shadow 与 Canary；质量退化自动回滚。
ADR-017
研究过程完整性与建模数据就绪度必须独立表达；no_eligible_public_data 不能计为 data ready，evidence_limited 的终态含义由具体 Goal Contract 决定。
ADR-018
LCA 外部资料检索以 Evidence Requirement Matrix、过程族 Document Route 和字段级 EvidenceObservation 为核心；修复必须改变因果输入，并用证据漏斗和关键字段覆盖的正向增量证明有效。
