01 / 15

执行摘要

项目应从“人通过对话临时编排 Agent 和脚本”升级为“目标驱动、事件驱动、Artifact 驱动”的自治知识生产系统。

核心结论
本项目不需要一个更强的“超级 Agent”，而需要一个长期运行的控制平面。Agent 可以犯错，但必须无法无证写入、无法静默漏做、无法给自己签字；错误应由独立机制发现、回滚并生成修复任务。

从哪里出发

仓库已拥有名称图 Gate、跨行业 lint、Wiki 批次状态机、BOM 探针和 LCA 绑定等执行原语，但入口、状态、协议和发布语义分散。

建设什么

建设统一 Kernel、Capability Registry、声明式 Workflow、不可变 Artifact Store、分层 Gate、Repair Controller 和异常队列。

最终状态

系统持续扫描全局缺口，自动生成任务、调用脚本与 Agent、验证和发布低风险变更；人只维护政策、裁决异常和执行专家签署。

预期收益

维度当前形态目标形态
驱动方式对话中由人逐步推进Desired State 与仓库现状自动对账
Agent 角色兼任计划、执行、检查和汇报只做候选生成或独立语义裁决
运行状态散落在聊天、文件名和局部 journal统一 State DB + Event Log
产物脚本直接写共享目录不可变 Artifact，经 Gate 后原子发布
失败处理人阅读日志后重新发起对话错误分类、自动重试、回滚、修复或隔离
质量声明多个局部 PASS 容易被外推为整体完成每个 Gate 明示证明范围，发布资格独立计算
02 / 15

背景与问题定义

方法论和局部 Workflow 已较成熟，但执行仍依赖人在对话中维持全局上下文，导致规则落实、状态连续性和错误恢复缺乏系统保证。

现有优势

  • 名称图已建立 Product / Activity、PRODUCES / CONSUMES、身份刻面和 A–E 不变量。
  • gate.py 已实现物化、对账、11/11 校验和原子发布。
  • wiki_batch.py 已实现计划、准备、核验、冻结、Gate、Apply、Publish 和 resume。
  • 跨行业 GPID、BOM 探针、产品系统树和 LCA 数据集绑定均已有可复用脚本。
  • 节点 Wiki 复盘已经积累大量真实失败样本，可作为缺陷语料库。

结构性问题

控制问题

  • 全局下一步由对话决定。
  • 多个入口实现相近流程。
  • 局部 journal 不能形成全仓状态。
  • 失败后依赖人工解释日志。

质量问题

  • 来源通过被误当成断言通过。
  • Gate 覆盖范围未被显式表达。
  • Agent 运行模型、工具和预算可能漂移。
  • 抽样完成容易被外推为全量完成。
设计边界：本方案不能证明开放领域知识“绝对无错”，也不取消专家对边界、刻面、数据代表性和定量值的责任。它要保证的是：错误影响有界、不可静默发布、可以追溯、可以回滚，并能把已知错误转化为永久防线。
03 / 15

目标、非目标与设计原则

所有模块、Skill、Workflow、脚本和 Agent 都必须服从同一组项目级不变量。

建设目标

  • 自动发现整个骨架数据库的行业、节点、分类、接口、Wiki 和绑定缺口。
  • 自动生成可重放 Job，并按依赖、风险、价值和预算调度。
  • 将 Agent 限制为可验证的候选生成器或裁决器。
  • 所有写入经过分层 Gate、事务 Apply、版本发布和发布后验证。
  • 低风险任务逐步实现无人值守，高风险任务自动转入最小异常包。

非目标

  • 不构建一个拥有无限权限、可直接编辑全仓的超级 Agent。
  • 不将聊天历史作为生产状态或权威知识。
  • 不以一个“总分”替代图、证据、内容、绑定和发布的分层质量声明。
  • 不在第一阶段引入重型分布式编排平台或一次性重写所有脚本。

六条硬原则

Job 驱动

每次工作必须来自持久化 Job，输入、预算、权限、结果和状态转移均可重放。

无直接写入

Agent 只提交 proposal 或 verdict；权威文件只能由受控 Apply capability 修改。

不可变产物

中间结果内容寻址、只增不改；新的计算产生新 Artifact，而不是覆盖历史。

证明后发布

发布必须携带输入哈希、运行证明、Gate 报告、政策版本和回滚目标。

集合守恒

应处理、已提名、已检索、已核验、已写入和已发布的集合逐层对账，禁止静默漏项。

缺陷固化

每个逃逸错误必须形成 fixture、mutation 或政策测试，并追溯扫描既有发布物。

跨模块问题如何处理

例如 Wiki 发现节点身份可能有误时，只发布 graph.identity_issue_detected，由 Planner 生成图修复任务。Wiki 不得直接修改名称图。图修复发布后，影响分析器根据 spine hash 自动使相关 Wiki、跨链和绑定进入 stale 状态并重建。

Skills、Memory、脚本与 Workflow 的统一管理

四类组件必须拥有清晰的职责和唯一权威来源，避免同一规则散落在 AGENTS、Skill、方法文档、Prompt 和脚本中。

组件负责什么不负责什么权威载体
Skill意图路由、参数收集、状态解释、异常交互生产状态、业务真相、直接写文件Skill package + workflow reference
Memory政策、结构化决策、运行历史、缺陷经验未验证聊天结论、隐式下一步Policy / ADR / State DB / Defect Corpus
Script单一、确定性、幂等 Capability全局编排、自由语义判断、越权发布Capability manifest + executable
Agent候选生成或独立语义裁决自证、自签、直接 ApplyAgent definition + prompt + schema
Workflow声明步骤、依赖、重试、预算、分支和 Gate复制业务规则、内嵌大段实现Versioned workflow specification
Gate证明一个声明范围内的属性宣称超出覆盖范围的整体正确Gate capability + policy + tests

Skill：薄入口

未来 generate-node-wiki 等 Skill 只负责识别任务并调用 workflow://wiki-node-production@v3。Skill 可以解释前置条件和异常，但不能保存状态机、重复生产规则或自行 Apply。

Memory：四层分离

规范性 Memory

Policy 与机器可读规则，定义 Gate、预算、风险、状态和发布资格。

决策 Memory

版本化 ADR，保存原因、证据、适用范围、替代关系和生效版本。

运行 Memory

Job、Run、Event、Artifact、usage、lease、错误和恢复点。

临时 Context

单次 Agent 调用的冻结 dossier、精简索引、evidence 和 task policy。

运行状态不能继续由聊天和目录命名承载。第一阶段采用 SQLite + 本地内容寻址 Artifact Store，后续可平滑迁移 PostgreSQL 和对象存储。

Artifact Store

var/artifacts/sha256/ab/cd/abcdef...

artifact://graph/steel/release@sha256:...
artifact://wiki/ict/P042/claim-proof@sha256:...

生产 Artifact 永不原地修改。docs/、wiki/ 和 registry/ 是 Release Manager 生成或更新的正式投影，不是运行缓存。

失效传播

每个 Artifact 记录上游依赖。当 graph spine hash 变化时，影响分析器自动将依赖它的 Wiki dossier、cross-link、LCA binding 和 product-system model 标为 stale，并生成局部重建任务。

09 / 15

质量保障与自治修复

系统不假设 Agent 正确，而是将错误限制在 candidate 区，并用独立证据、分层 Gate、故障注入和回滚形成闭环。

七层 Gate

层检查内容主要发现
G0 运行证明模型、工具、argv、sandbox、预算、事件模型漂移、越权联网、预算失控
G1 协议完整性Schema、任务 ID、节点 ID、哈希ID 漂移、字段遗漏、伪造产物
G2 输入覆盖节点、章节、claim 集合守恒原子化漏句、静默跳过
G3 证据一致性URL、locator、excerpt、content hash摘录污染、引用错位
G4 语义一致性目标节点 EXACT 对齐、原文蕴含相邻对象错绑、过度外推
G5 内容合同章节、表归属、节点特异性、非退化薄页、模板壳、Product/Activity 混写
G6–G7 全局与发布图、跨链、coverage、风险、hash lock抽样冒充全量、旧报告复用、跨模块冲突

Proof-carrying Claim

每个外部事实必须携带节点身份哈希、来源身份、locator、原文摘录、内容哈希、对齐维度和独立 verdict。没有证明对象的内容最多进入 draft，不得升级 reviewed。

Gate Mutation Score = 被 Gate 阻断的注入错误数 ÷ 总注入错误数。Gate 自身只有达到规定 mutation score，才允许保护生产发布。

第一条生产切片的完成条件

  1. 可从统一 CLI 为一个 Wiki 节点创建 Job。
  2. 所有输入、模型、工具和政策版本冻结。
  3. Nomination、Search/Fetch、Verify、Assemble、Gate、Apply 和 Publish 可断点恢复。
  4. 历次复盘中的已知错误全部进入 defect corpus。
  5. Gate mutation 达到阈值，错误不能进入正式 Wiki。
  6. 失败可以自动重试、回滚或生成最小人工异常包。
  7. 发布 manifest 可完整重放并验证。

项目完成度定义

“整个骨架数据库完成”应由机器可计算的项目政策定义，包括：所有计划行业达到声明生命周期；图 Gate 全过；分类缺口已清或已解释；跨行业接口无未响应项；GPID 无断链；Wiki 达到规定覆盖；长尾和数据缺口显式；专家签署任务完成。项目进入维护态后，完成度仍会因新分类、新技术和新行业期望变化而重新计算。

关键架构决策

以下决策应进一步拆成版本化 ADR，并成为重构期间的边界护栏。

ADR-001
采用模块化单仓 + 本地控制平面，不立即拆成微服务。
ADR-002
第一阶段使用 SQLite 和本地内容寻址存储，保留迁移 PostgreSQL/对象存储的接口。
ADR-003
Agent 永不直接写权威库，只产生 proposal/verdict。
ADR-004
所有跨模块交互使用 Artifact 和 Event，不通过共享文件的隐式编辑。
ADR-005
Workflow 声明式、Capability 注册化、Agent 定义版本化。
ADR-006
Source verified、Claim verified、Wiki reviewed、Dataset ready 是四个独立状态。
ADR-007
Gate 必须声明证明范围；总发布资格由多个 Gate 组合计算。
ADR-008
复盘缺陷永久进入测试和追溯扫描，不允许只修当前样本。
ADR-009
人在主流程中逐步退出，但政策变更、身份边界和定量专家签署长期保留人工责任。

最终判断
